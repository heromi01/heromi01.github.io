정적 웹 환경에서의 보안과 실시간 클라우드 DB 연동기

GitHub Pages의 무서버 환경에서 Supabase PostgreSQL을 연동하며 고민한 최소 권한 RLS, 서버사이드 RPC 인증, 그리고 앞으로 해결해야 할 기술적 과제들

📅 2026.09.16
✍️ 작성자: heromi01
🏷️ Supabase, GitHub Pages, PostgreSQL, RLS, Web Security

1. 배경: 정적 웹 호스팅의 태생적 한계와 클라우드 DB 도입

GitHub Pages는 서버리스 정적 파일(HTML, CSS, JS) 호스팅 서비스입니다. 자체 백엔드 서버(Node.js, Python, Java 등)를 구동할 수 없기 때문에 초기에 구축한 방명록은 브라우저의 localStorage에 데이터를 보관하는 방식이었습니다.

그러나 localStorage 방식은 "글을 작성한 해당 브라우저에서만 데이터가 보존"된다는 치명적인 한계가 있었습니다. 외부 방문자가 스마트폰이나 다른 PC로 접속했을 때 서로의 방명록과 공감(Like)을 실시간으로 공유할 수 있는 진정한 커뮤니티 공간으로 진화시키기 위해, 클라우드 PostgreSQL 기반 BaaS인 Supabase와의 연동을 결정했습니다.

2. 보안 설계: 비밀키 분리와 Git 추적 방지 전략

정적 호스팅 환경에서 클라우드 데이터베이스를 연동할 때 가장 위험한 점은 "누구나 개발자도구(F12)나 GitHub 공개 저장소의 코드를 열어볼 수 있다"는 점입니다. 이를 방어하기 위해 다음과 같은 보안 원칙을 수립하고 적용했습니다.

⚠️ 절대 노출되어서는 안 되는 비밀키
데이터베이스의 모든 RLS를 우회하고 테이블을 직접 조작할 수 있는 service_role 비밀키와 관리자 마스터 키는 Git 저장소 및 프론트엔드 코드에 1바이트도 포함되지 않아야 합니다.

① 공개 키와 비밀 키의 역할 분리

  • Publishable / Anon Key: 브라우저에 공개되는 키로, 오직 데이터베이스의 RLS(행 단위 보안) 정책이 허용하는 행위만 수행 가능합니다.
  • Service Role Key: 데이터베이스 전체 관리자 권한 키로, 프론트엔드나 Git에 올리지 않고 향후 Supabase Edge Functions 서버 환경 내에서만 격리 운용합니다.

② Git 추적 방지 (.gitignore)

로컬 개발 및 향후 백엔드 작업 시 생성될 수 있는 모든 환경변수 파일(.env, .env.local, *.key, *.secret)을 사전에 .gitignore에 명시하여 민감한 키가 GitHub에 커밋되는 사고를 원천 차단했습니다.

3. 최소 권한 원칙(Least Privilege) RLS 및 서버사이드 RPC

데이터베이스 테이블 guestbook에 Row Level Security (RLS)를 활성화하여 익명 사용자의 직접 조작을 철저히 제한했습니다.

DML 동작 적용된 RLS 정책 보안 통제 방식
SELECT Allow public read access 모든 방문자가 글 목록을 조회할 수 있도록 허용
INSERT Allow public insert 닉네임(1~50자), 본문(1~1000자) 유효성 통과 건만 허용
UPDATE Deny direct public update 클라이언트의 직접 UPDATE 원천 차단 (거부)
DELETE Deny direct public delete 클라이언트의 직접 DELETE 원천 차단 (거부)

비밀번호 노출 없는 안전한 수정/삭제: SECURITY DEFINER RPC

클라이언트에서 비밀번호를 검증하려면 원래 DB에서 비밀번호 컬럼을 읽어와야 하지만, 이는 남의 비밀번호를 볼 수 있는 심각한 보안 결함이 됩니다. 이를 해결하기 위해:

  1. 공개 뷰(guestbook_public)를 생성하여 클라이언트 조회 시 password_hash 컬럼 자체를 아예 배제했습니다.
  2. 수정과 삭제는 Postgres 내부 함수인 verify_and_update_guestbook과 verify_and_delete_guestbook을 SECURITY DEFINER로 실행하여, 비밀번호 및 마스터 키(0000) 대조가 서버 내부에서만 조용히 일어나도록 설계했습니다.

4. 관리자 작업 분리를 위한 Supabase Edge Functions 아키텍처

현재 적용된 PostgreSQL RPC 방식에서 한 걸음 더 나아가, 향후 대규모 트래픽이나 복잡한 비즈니스 로직을 처리하기 위해 Supabase Edge Functions로 관리자 작업을 분리하는 아키텍처를 설계했습니다. 

[ 브라우저 (클라이언트) ]
       │
       ├─ (일반 조회 / 등록) ──> [ Supabase REST API ] ──> [ RLS 필터링 ] ──> [ DB Table ]
       │
       └─ (관리자 강제 삭제 / 필터링)
               │
               ▼
   [ Supabase Edge Function (Deno) ]
   - Secrets 환경변수: MASTER_ADMIN_KEY, SERVICE_ROLE_KEY 보관
   - IP Rate Limiting 및 Brute-force 공격 방어
   - AI 기반 악성 스팸 텍스트 자동 검열
               │
               ▼ (service_role 안전 호출)
       [ Supabase PostgreSQL DB ]

5. 🔥 앞으로의 작업 고민 내용 (Future Challenges & Roadmap)

현재 최소 권한 RLS와 서버사이드 함수를 통해 기본적인 보안과 데이터 저장을 성공적으로 구축했으나, 지속 가능하고 안전한 오픈 방명록 서비스를 운영하기 위해 다음과 같은 핵심 기술적 고민 사항들이 존재합니다.

🛡️ 1. 악성 봇 및 스팸 도배 방어 (Anti-Abuse / Rate Limiting) 최우선 과제

현재는 누구나 API를 통해 방명록을 등록할 수 있으므로, 악성 봇이 자동화 스크립트로 수천 개의 스팸 글을 밀어넣을 경우 DB 용량 초과 및 사이트 훼손 위험이 있습니다.
고민 포인트: 사용자 경험을 해치지 않는 투명한 캡차(Cloudflare Turnstile 등)를 프론트에 도입할 것인가, 아니면 Supabase Edge Function을 프록시로 두어 IP 기반 호출 횟수 제한(Rate Limit)을 걸 것인가?

⚡ 2. 실시간 웹소켓(Supabase Realtime) 도입과 리소스 비용 성능 / UX

현재는 새로고침이나 등록 시점에만 DB를 갱신합니다. 다른 사용자가 새 글을 쓰거나 하트(공감)를 눌렀을 때 화면이 실시간으로 갱신되는 웹소켓 구독(Realtime)을 도입하면 인터랙티브한 경험이 극대화됩니다.
고민 포인트: 무료 티어에서 Realtime 연결(Connection) 수 한계 및 모바일 기기에서의 배터리/네트워크 소모를 고려했을 때, 폴링(Polling) 방식과 웹소켓 방식 중 어느 것이 더 효율적인가?

❤️ 3. 공감(Like) 어뷰징 방지 및 익명 사용자 식별 데이터 무결성

현재 공감 상태는 브라우저의 localStorage에 저장되므로, 방문자가 시크릿 모드를 열거나 캐시를 지우면 동일한 글에 무한정 좋아요를 누를 수 있는 취약점이 있습니다.
고민 포인트: 완전한 회원가입 없이 익명성을 보장하면서도 중복 공감을 차단하기 위해, Supabase의 Anonymous Sign-in(익명 인증)을 적용하여 1인 1공감 DB 제약 조건을 거는 방안을 검토 중입니다.

🔐 4. 마스터 키 체계의 진화: 고정 키에서 관리자 세션 분리로 아키텍처 고도화

현재는 DB 서버 함수 내부에 마스터 비밀번호가 존재합니다. 안전하게 은닉되어 있지만, 향후 비밀번호를 변경하려면 DB 마이그레이션이 필요합니다.
고민 포인트: 관리자인 heromi01 본인만 GitHub OAuth 또는 이메일 매직 링크(Magic Link)로 로그인하여 관리자 토큰(JWT)을 획득하고, 이 토큰이 검증될 때만 관리자 전용 삭제 API가 승인되도록 고도화할 계획입니다.

💾 5. 정기적인 데이터 백업 및 아카이빙 자동화 운영 안정성

클라우드 DB 무료 티어의 경우 일정 기간 활동이 없으면 프로젝트가 일시정지(pause)될 수 있습니다.
고민 포인트: GitHub Actions 크론(Cron) 스케줄러를 구성하여 매주 방명록 데이터를 안전한 JSON 아카이브 파일로 자동 커밋/백업받는 무중단 데이터 보존 파이프라인 구축을 고려하고 있습니다.

  • [✓] 비밀번호 컬럼 비노출: guestbook_public 뷰를 통해 클라이언트 전송 차단
